# 실제 과제 분석

1. 현재 작업 폴더를 확인한다. **실제 과제 README 및 당일 운영 규칙**이 최우선. 키트/예제 파일을 과제 요구로 오해하지 않는다.
2. 필수 요구/예외/단서(단, 제외, 특정 경우)/제출 경로/형식/금지를 문장별로 뽑고 R-ID를 부여한다. 역할별 동작, 데이터 변경 시 결과 갱신, 실패·경계 케이스까지 포함한다.
3. **전체 데이터셋 감사(Data Audit):** 실제 과제 폴더에서 입력 데이터셋과 변경 시나리오를 빠짐없이 열거하고, 각각의 목적·행/열 수·컬럼 형식·기본키/외래키/파일 간 조인 관계를 설명한다. 실제 데이터를 읽어 결측·중복 행/키·누락 ID·값 범위·NaN/음수·날짜/시간대/교대·시간 순서 오류를 검사한다. 데이터셋 간 차이와 동적 재계산 영향도 확인한다. **파일별 표로 조사 근거(명령·전체/표본/NOT_RUN)와 문제 건수·구현 영향**을 사용자에게 보고한다. 열람·검사하지 못한 데이터는 정상으로 추정하지 않는다. 원본 데이터를 수정하거나 원문 개인정보를 노출하지 않는다. 과제별 원본/산출물 예시와 기존 테스트를 먼저 확인하고, `scripts/data_tools.py`는 적합할 때만 선택 사용.
4. **사실(README) / 실제 데이터 관찰 / 가정 / 미확정 정책**을 분리한다. 담당자에게 물을 업무 사실은 참가자가 직접 확인한다.
5. **전체 데이터셋 감사를 실제로 마친 후, Cofa 과제 담당자에게 참가자가 직접 전달할 현업 확인 질문 목록을 초기 분석의 필수 산출물로 만든다.** 단순한 명세 미확정뿐 아니라 **과제 도메인의 업무 배경·사용자 불편·현행 프로세스·개선 목적·성공 KPI**를 이해하기 위한 질문도 과제와 관련성이 있으면 생성한다. 예: 통근 노선 과제라면 `기존 운영에서 직원들의 주요 불만이나 불편은 무엇인가요?`, `현재 운영 방식에서 반복적으로 발생하는 문제는 무엇인가요?`, `이번 개선의 핵심 성공 지표는 무엇인가요?`, `노선 변경 업무에서 병목은 어디인가요?`. 특정 불만이 실제로 있다는 사실을 추정하거나 담당자의 답을 만들어내지 않는다. README·제공 CSV·기존 코드에서 이미 답이 확정된 질문, 단순 코딩 세부사항, 업무 관련성이 약한 추측은 제외한다. **과제에 직접 연결되는 정성적 현업 질문은 데이터셋에 답이 없다는 이유로 제외하지 않는다.** 질문은 `Q-ID | 분류(업무 배경·사용자 불편·성과 지표·운영 규칙·데이터 예외 등) | 우선순위(P0/P1/P2) | 확인 대상(Cofa 과제 담당자/참가자) | 질문 원문 | 질문 근거(README·데이터 관찰·업무 목적상 정보 공백) | 답변에 따라 달라지는 설계·검증·우선순위 | 상태`로 적는다.
   - **P0:** 답 없이 필수조건 또는 계산의 타당성을 확정할 수 없음. **P1:** 현업의 핵심 불편·개선 목표·성과 지표나 주요 운영·최적화 선택에 영향. **P2:** 편의·후속 개선. 현업의 경험과 문제 인식은 실제 담당자에게 문의하고, 최적화 우선순위처럼 참가자가 결정할 설계 판단과 혼동하지 않는다. **P1/P2 도메인 질문은 미응답이어도 그 자체로 개발 중단 사유가 아니다.**
   - 첫 응답에는 전체 우선순위 질문 목록을 **한 번에 보여주되**, 실제 현업 문의는 참가자가 담당자에게 직접 **한 건씩** 전달한다. 사용자에게 내릴 정책 결정도 `cofa-decide`에서 **한 번에 한 건씩** 물어본다. 질문 목록을 보여 주는 것과 복수의 결정을 동시에 요구하는 것은 다르다.
   - 질문이 하나도 없다면 **`현업 확인 질문 없음 — 근거: ...`**을 명시한다. 답변받은 항목은 `CONFIRMED(답변 근거)`, 미응답은 `OPEN`으로 남긴다. 미응답을 AI 추측으로 확정하지 않으며, 결정과 무관한 작업은 계속할 수 있다.
6. **개발 계획·전략:** 기존 폴더 구조를 보고 필수 R-ID 우선순위, 기술 스택/데이터 흐름, 알고리즘 대안, 데이터 변경 후 재계산, 실패 처리, 자동 테스트와 UI UAT를 제안한다. 현업 확인 질문 목록과 이 계획을 사용자에게 먼저 보고한 후 핵심 사용자 설계 판단은 `cofa-decide`로 넘긴다. 답변을 받으면 요구사항과 테스트 기준을 갱신한다. **분석·감사·질문 목록·계획을 보고하기 전에는 본격적인 구현을 시작하지 않는다.** 데이터 검사를 위한 읽기 전용·임시 분석 코드는 허용한다.
7. 질문·요구사항을 여러 README/PLAN/REQUIREMENTS 파일에 중복 기록하지 않는다. **기존 작업 기록이 있으면 거기에**, 없으면 초기 응답에 목록을 표시하고 필요할 때만 최소 한 파일에 기록한다. 실제 제출물 형식이 우선이다.

**금지:** 사용자가 승인하지 않은 원본 입력 변경, 업무 목표 임의 확정, 스택 변경·새 문서/폴더 과생성. 미정 조건이 있어도 무관한 데이터 검사와 독립 구현은 가능하다.
