# 실제로 확인한 것만 PASS

1. 필수 R-ID별로 소스·함수·입력/출력·기대 결과·검사 명령/사용자 확인 여부·**현재 코드 판본**을 대조한다. `dropped`, `skip`, `NOT_RUN`, `BLOCKED`, `STALE`은 필수조건 성공이 아니다.
2. 정상·실패·경계 케이스를 실제 실행한다. 결과를 근거로 예상값을 뒤바꾸지 않는다. 검사 0건, 서버 시작, 파일 존재만으로 전체 성공을 주장하지 않는다.
3. 알고리즘·분석 결과는 가능한 한 **독립적인 작은 입력/손 계산/불변조건 검사**로 재검산한다. 특히 관계키 중복·행 증폭, 중복 배정·누락, 용량, 시간 경계 등을 확인한다.
4. 실제 과제에 관련된 입력 누락·중복·0건·음수/NaN, 야간조·휴일, 변경 후 재계산, 역할별 서버 권한, 데이터 지속성·동시 수정, 복구·한계를 영향도 순으로 검증한다. 위험이 없으면 억지로 새 프레임워크/테스트 인프라를 만들지 않는다.
5. UI는 `../../prompts/UAT.md`에 따라 **사용자가 한 건씩 직접 Browser에서 테스트**한다. 기대 결과를 먼저 제시하고 사용자의 관찰을 기다린다. 사용자 PASS/FAIL은 **핵심 정책 결정의 승인 신호가 아니다**.
6. FAIL이면 원인 조사→승인 범위 내 최소 수정→같은 실패 테스트+관련 정상 테스트→해당 UAT 재확인. 정책 변경이 필요할 때만 새로운 HITL. 테스트 이후 영향 받은 코드·입력이 바뀌면 관련 검증은 STALE로 두고 재실행한다.
7. 제출 전 필수 산출물의 실제 경로·형식·파일명 확인, PASS/FAIL/NOT_RUN/STALE 개수 및 미해결 문제·실제 위험을 정리한다. 테스트 통과를 만들어내지 않는다.

**도구:** `scripts/data_tools.py`, `scripts/source_guard.py`, `examples/shuttle/verify_routes.py`는 선택형 로컬 도구이며 실제 과제 유형과 맞을 때만 사용. 통근버스 예제는 공식 채점기나 최적화 엔진이 아니다.
