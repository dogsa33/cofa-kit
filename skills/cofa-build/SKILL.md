# 구현 및 수정 원칙

실제 과제의 README, 기존 코드, 확정된 요구사항(R-ID), 참가자가 직접 선택한 결정(D-ID)을 우선 확인합니다. **신규 과제에서는 `cofa-triage`의 4단계 사전 결과(요구사항 분석 → 전체 데이터 감사 → 현업 확인 질문 목록 → 개발 계획)를 사용자에게 먼저 보고한 후 본격 구현합니다.** 기존 프로젝트의 작은 수정·검증에서는 영향받은 범위만 재확인하며 이미 검증된 분석을 반복하지 않습니다.

1. **최소 수정:** 기존 언어·서버·DB·테스트 구조를 우선 재사용합니다. 필요성을 설명할 수 없는 새 파일, 프레임워크, UI 장식이나 중복 문서를 만들지 않습니다.
2. **실제 데이터 흐름:** 입력 → 유효성 검사 → 처리 → 저장 → 역할별 결과 표시까지 구현합니다. 실제 입력을 바꿨을 때 결과도 바뀌어야 합니다. 고정 예제 결과를 실제 계산으로 표시하지 않습니다.
3. **의사결정 경계:** 승인받은 작업 범위의 일반 코드 작성, 오류 수정, 회귀 테스트는 자율적으로 합니다. 정책, 우선순위, 개인정보·접근 권한, 중대한 구조 변경처럼 사용자의 판단이 필요한 사항은 `cofa-decide`에 따라 한 번에 하나씩 질문하고 명시적인 답변을 받은 뒤 진행합니다. 답변을 받기 전에는 해당 판단에 의존하는 구현을 확정하지 않습니다.
4. **실패와 수정:** 실패 사례를 재현하고 가장 작은 범위로 고친 뒤 동일 사례와 관련 정상 동작을 다시 검사합니다. 테스트 실패를 성공으로 바꾸거나 검증하지 않은 기능을 완료로 기록하지 않습니다.
5. **파일 점검:** 추가·변경·삭제한 파일의 필요성, 관련 필수 요구와 검증 근거를 확인합니다. 위험한 삭제는 사전에 허락을 받습니다.
6. **단일 세션:** 서브에이전트나 병렬 위임은 사용하지 않습니다. 외부 전송, 비인가 도구 연결 또는 자동 설치 없이 허용된 로컬 환경에서 작업합니다.

실제 기능 검증과 사용자의 브라우저 확인은 `cofa-verify` 지침으로 이어 갑니다. **코드 구현 완료와 기능 검증 성공은 서로 다릅니다.**
