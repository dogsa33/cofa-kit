# 본인이 설명할 수 있는 실제 구조

- 누가 무엇을 넣으면 **실제** 어떤 파일/함수/API/DB 저장·계산·화면을 거쳐 결과가 나오는지 5~8단계로 설명한다. 가능하면 작은 입력값 하나를 추적한다.
- 실제 사용자 D-ID별 선택/명시적 거절/미선택/AI 제안을 구분하고, **선택 이유를 사용자 발언에 없는 내용으로 만들지 않는다**. 해당 결정이 현재 코드에 반영됐는지 확인한다.
- AI가 작성·수정한 내용과 사용자가 직접 결정·클릭·확인한 내용을 분리한다. 사용자 검증이라고 쓰려면 실제 사용자 보고가 있어야 한다.
- 자동 테스트·수동 UAT 결과와 FAIL/NOT_RUN/STALE을 구분하고, 아키텍처·알고리즘의 취약점 및 규모·동시성 한계를 설명한다.
- **제출 전 설명 가능성 점검: 예상 질문·답변 목록을 필수 산출한다.** 실제 과제의 구현·결정·테스트 이력에 근거해 출제 가능성이 높은 질문 **6~10개**를 선별하고, 각각 `질문(QA-ID) | 핵심 답변(2~5문장) | 실제 증거(파일·함수·API·D-ID·테스트) | 구현 여부·한계`로 작성한다. 질문이 많아지더라도 동일 내용을 중복 나열하지 않는다.
  - 과제에 맞는 항목을 우선 선택한다: **프론트엔드/백엔드/DB/API와 실행 구조, HTTPS·인증·인가, 알고리즘과 대안·복잡도, 데이터 변경/자동 재계산, 이상치·극단적 케이스, 동시 접속·동시 수정·자원 한계, 자동/수동 검증, AI에 맡긴 일/묻지 않은 일, 사용자 선택·거절과 근거, 남은 취약점·개선안**.
  - 질문은 **실제 구현과 관련된 것으로만** 구성한다. HTTPS 미구현·동시 접속 미검증 등은 구현한 것으로 꾸미지 말고 `미구현/미검증 → 잠재적 위험 → 개선 방향`으로 설명한다. 알 수 없는 값·정책·의도는 `확인되지 않음`으로 쓴다.
  - **AI에게 무엇을 요청하지 않았는지**는 실제 대화·작업 기록에서 뒷받침되는 경우에만 언급한다. 전체 AI 대화 이력을 확인하지 못하면 `검토한 기록 범위에서는 확인되지 않음`으로 표현하고 사실처럼 단정하지 않는다.
  - 목록 작성 후 참가자가 **직접 설명할 수 있는지** 자기 점검하도록 안내한다. 사용자 요청 없이 추가 코드 작성이나 필수 검증을 대신하지 않는다.
- 기존 과제의 필수 제출 문서·형식이 우선이다. FINAL_REVIEW.md 하나를 제외하고 필요 없는 보고서·서브에이전트 로그는 만들지 않는다.
- **FINAL_REVIEW.md 단일 최종 검토 파일:** 제출 확정 전에 실제 과제 폴더 최상위에 FINAL_REVIEW.md를 생성·갱신한다. .cofa-kit 내부에는 생성하지 않는다. 구현·검증 요약과 예상 질문·답변 6~10개를 한 파일에 담고 중복 요약 문서는 추가하지 않는다. 대화창에는 파일 경로·저장 확인·핵심 요약만 보고한다.
- **원문 텍스트 가독성:** Cofa IDE는 Markdown을 렌더링하지 않을 수 있으므로 FINAL_REVIEW.md 내용은 파일 확장자와 상관없이 일반 텍스트로 적는다. 제목은 1. 과제 개요, 2. 구현 결과와 같이 평문 숫자로 쓰고, 설명은 - 항목으로 구분한다. 굵게 표시하는 **, # 제목, | 표, 코드 펜스, > 인용, Markdown 링크는 최종 파일에서 사용하지 않는다.
- **최종 보고서 구성:** 1. 과제 개요 / 2. R-ID별 구현·미구현 / 3. 데이터셋 감사·처리 흐름 / 4. 프론트엔드·백엔드·DB·API·HTTPS/인증 구조 / 5. 알고리즘·비교 대안·HITL·AI 활용·AI에 묻지 않은 사항 / 6. 실제 자동 테스트·UAT 결과 및 **전체 사용자 직접 확인 시나리오 목록** / 7. 극단적 상황·동시 접속·성능·보안 취약점 / 8. 예상 서술형 질문·답변 6~10개.
- **6번 항목 필수 조건:** **개발 중 사용자 UAT를 요구하지 않으며, 최종 한 차례 사용자 종합 검증에서 전체 체크리스트를 제시하고 결과를 묶어서 반영한다.** 실제 과제의 **모든 필수 R-ID에 대한 UAT 커버리지**를 확인하고, UI 기능마다 UAT-ID / R-ID / 계정·사전조건 / **사용자의 직접 조작 절차** / **사전 예상 결과** / 사용자 실제 관찰 / PASS·FAIL·NOT_RUN·BLOCKED·STALE / 검증 근거·판본을 개별로 정리한다. 미실행 시나리오도 목록에서 지우지 않는다. UI로 검증 불가능한 요구는 자동/API/독립 검산 항목으로 별도 연결하며 미실행·미검증 이유를 적는다. **전체 예정 사례 수, 실제 사용자 PASS/FAIL, NOT_RUN/BLOCKED/STALE, R-ID별 미확인 기능과 제출 위험**을 함께 요약한다. 사용자 확인이 없으면 PASS라고 기록하지 않는다. 새 검증 파일을 만들지 않고 기존 기록에서 FINAL_REVIEW.md를 갱신한다.
- **Q&A 평문 서식:** Q1. 왜 해당 알고리즘을 사용했나요? 다음에 - 답변: 실제 구현 설명, - 근거: 파일·함수·D-ID·테스트 결과, - 한계: 미구현·미검증과 위험을 2~5문장으로 기술한다. 사실 근거 없는 구현 주장과 사용자 선택 이유 창작은 금지한다.
- 마지막 5분에 처음 작성하지 말고 결정·검증 기록을 개발 과정에서 축적해 제출 전에 정리한다. 최종 코드 변경으로 검증이 무효화되면 상태를 갱신한다. 개인정보 원문·키·민감한 시험 데이터를 불필요하게 중복 저장하지 않는다.
- **과제 예외:** 실제 과제가 추가 파일 생성 또는 제출 파일 목록을 엄격하게 제한한다면 FINAL_REVIEW.md를 생성하지 않는다. 대신 동일한 평문 요약과 Q&A를 Codex 대화창에 출력하고 이유를 알린다. 시간이 부족하면 필수 검증과 제출을 우선한다.
- **예상 Q&A는 제출 확정 전, 실제 구현을 이해하기 위한 사전 자기점검 자료일 뿐이다.** 제출 확정 후 AI 사용 금지 단계에서는 예상 문항·답변을 새로 생성·수정하거나 실제 후속 서술형을 대신 풀지 않는다. **제출이 확정됐거나 AI 사용 금지 단계이면 즉시 중단한다.**
