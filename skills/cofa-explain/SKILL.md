# 본인이 설명할 수 있는 실제 구조

- 누가 무엇을 넣으면 **실제** 어떤 파일/함수/API/DB 저장·계산·화면을 거쳐 결과가 나오는지 5~8단계로 설명한다. 가능하면 작은 입력값 하나를 추적한다.
- 실제 사용자 D-ID별 선택/명시적 거절/미선택/AI 제안을 구분하고, **선택 이유를 사용자 발언에 없는 내용으로 만들지 않는다**. 해당 결정이 현재 코드에 반영됐는지 확인한다.
- AI가 작성·수정한 내용과 사용자가 직접 결정·클릭·확인한 내용을 분리한다. 사용자 검증이라고 쓰려면 실제 사용자 보고가 있어야 한다.
- 자동 테스트·수동 UAT 결과와 FAIL/NOT_RUN/STALE을 구분하고, 아키텍처·알고리즘의 취약점 및 규모·동시성 한계를 설명한다.
- **제출 전 설명 가능성 점검: 예상 질문·답변 목록을 필수 산출한다.** 실제 과제의 구현·결정·테스트 이력에 근거해 출제 가능성이 높은 질문 **6~10개**를 선별하고, 각각 `질문(QA-ID) | 핵심 답변(2~5문장) | 실제 증거(파일·함수·API·D-ID·테스트) | 구현 여부·한계`로 작성한다. 질문이 많아지더라도 동일 내용을 중복 나열하지 않는다.
  - 과제에 맞는 항목을 우선 선택한다: **프론트엔드/백엔드/DB/API와 실행 구조, HTTPS·인증·인가, 알고리즘과 대안·복잡도, 데이터 변경/자동 재계산, 이상치·극단적 케이스, 동시 접속·동시 수정·자원 한계, 자동/수동 검증, AI에 맡긴 일/묻지 않은 일, 사용자 선택·거절과 근거, 남은 취약점·개선안**.
  - 질문은 **실제 구현과 관련된 것으로만** 구성한다. HTTPS 미구현·동시 접속 미검증 등은 구현한 것으로 꾸미지 말고 `미구현/미검증 → 잠재적 위험 → 개선 방향`으로 설명한다. 알 수 없는 값·정책·의도는 `확인되지 않음`으로 쓴다.
  - **AI에게 무엇을 요청하지 않았는지**는 실제 대화·작업 기록에서 뒷받침되는 경우에만 언급한다. 전체 AI 대화 이력을 확인하지 못하면 `검토한 기록 범위에서는 확인되지 않음`으로 표현하고 사실처럼 단정하지 않는다.
  - 목록 작성 후 참가자가 **직접 설명할 수 있는지** 자기 점검하도록 안내한다. 사용자 요청 없이 추가 코드 작성이나 필수 검증을 대신하지 않는다.
- 기존 과제의 제출 문서에 맞춰 갱신한다. 별도 문서가 반드시 요구되지 않는다면 기존 최종 보고에 목록을 포함하고, 필요 없는 장문의 보고서·서브에이전트 로그를 만들지 않는다.
- **예상 Q&A는 제출 확정 전, 실제 구현을 이해하기 위한 사전 자기점검 자료일 뿐이다.** 제출 확정 후 AI 사용 금지 단계에서는 예상 문항·답변을 새로 생성·수정하거나 실제 후속 서술형을 대신 풀지 않는다. **제출이 확정됐거나 AI 사용 금지 단계이면 즉시 중단한다.**
