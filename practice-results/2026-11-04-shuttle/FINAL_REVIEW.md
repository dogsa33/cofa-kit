1. 과제와 제출 상태

- 실행 중 서버: 0.0.0.0:3000, 접속 http://localhost:3000 입니다. 서버는 사용자 UAT 동안 유지합니다.
- 코드: server.cjs, store.cjs, data.cjs, planner.cjs, verify.cjs, public의 HTML/JS/CSS입니다. 외부 패키지 설치 없이 Node.js 24 기본 모듈과 SQLite를 사용합니다.
- 필수 산출물: README_RUN.md, artifacts/route_plan.json, IMPLEMENTATION_REPORT.md, artifacts/test-results.txt를 저장했습니다.
- 기준 제출 JSON은 base v1/정책 v1이고, 사용자가 S1을 적용한 실행 DB는 데이터 v2입니다. 기준 산출물을 현재 UI 결과로 위장하거나 덮어쓰지 않습니다.
- 제출은 아직 확정되지 않았습니다. 참가자가 직접 제출하며 확정 후 Codex 작업을 중단합니다.

- 전체 원본 파일 SHA-256 전후 불변 검사를 자동 테스트에서 확인했습니다.

4. 실행 구조와 보안
- 단일 Node.js HTTP 서버가 정적 화면과 API를 제공합니다. SQLite가 현재 데이터/버전/정책/결과/이력/계정 해시/세션을 저장합니다. 계산은 worker thread로 분리합니다.
- ADMIN API는 모든 요청에서 역할을 확인합니다. 구성원 API는 직원 ID를 로그인 계정과 비교하고 타 직원 탑승객과 타 사업장 정보를 응답에서 제거합니다.
- scrypt와 개별 무작위 salt, 난수 세션 토큰의 SHA-256 저장, 세션 만료/로그아웃, HttpOnly와 SameSite=Strict, CSRF/Origin 검사, CSP, 출력 이스케이프, 매개변수 SQL, 입력 크기 제한, 로그인 시도 제한을 적용했습니다.
- HTTP 전송이며 HTTPS는 미구현입니다. 과제에서 외부 배포/HTTPS를 요구하지 않습니다. 전송 암호화가 없어 실제 공개 운영에는 TLS와 운영 인증 체계가 필요합니다.
- 외부 모델/API/지도 SDK/데이터 외부 전송/Computer Use/Browser 자동화를 사용하지 않았습니다. 로컬 HTTP API 테스트는 사용자 컴퓨터의 이 앱만 대상으로 했습니다.

6.1. 전체 Browser UAT 목록과 판정 원칙
- 전체 목록은 UAT01~UAT36입니다. 현재 PASS 2건, FAIL 0건, NOT_RUN 34건, STALE 0건입니다. UAT01과 UAT02는 위의 기존 절차/예상 결과/사용자 PASS 기록을 보존합니다. UAT03부터 아래 순서로 한 건씩 안내하고 실제 응답을 받은 뒤 다음 사례를 안내합니다.
- 공통 접속은 http://localhost:3000, 바인딩은 0.0.0.0:3000입니다. 운영자 admin_demo / AdminDemo!2026, 구성원 worker001 / Worker001!2026을 사용합니다. Browser는 사용자만 직접 조작합니다.
- N/P는 각 사례의 사전조건 설정을 마친 뒤 읽은 데이터/정책 버전입니다. base로 사전조건을 맞추는 적용도 버전을 증가시킵니다. 과거 v1/v2를 새 테스트의 고정 기대값으로 재사용하지 않습니다.
- B는 최대 승차시간, 평균 승차시간, 실제 차량 대수, 운행 횟수, 총 운행시간 순입니다. base+B의 기준 지표는 6대/174편/7503분/평균 35.107분/최대 55분/미배정 0/독립 위반 0입니다. 승인 정책이 바뀌면 그 정책에 맞는 기대를 새로 고정한 뒤 검사합니다.
- PASS는 안내한 기대를 실제 확인한 경우, FAIL은 불일치, NOT_RUN은 미수행/응답 대기/실행 불가/사전조건 미충족입니다. STALE은 변경으로 기존 검증의 적용 근거가 무효화돼 재검증해야 하는 경우입니다. 후속 스냅샷 적용만으로 과거 특정 입력의 성공 이력을 지우지는 않습니다.
- 실제 결과에는 사용자 발언, 관찰 범위, 버전, 확인 시각과 변경 영향을 기록합니다. PASS 한 단어만 받으면 세부 관찰을 창작하지 않습니다. 수정 후 영향받은 사례는 STALE로 표시하고 같은 사례를 다시 안내합니다.
- 자동 테스트 PASS는 Browser UAT PASS를 대신하지 않습니다. Console/API 주소 검사는 사용자가 이 앱의 동일 출처 로컬 API만 직접 호출합니다. Console 사용이 불가능하면 NOT_RUN과 사유를 남깁니다.
- DB 암호 해시, 전체 원본 불변성, 서버 재시작 실행 자체는 Browser만으로 입증할 수 없습니다. 관련 사례는 로컬 확인을 동반하고 Browser 관찰과 내부 증거를 분리합니다. 해당 확인을 못 하면 NOT_RUN으로 둡니다.
- 요구별 연결: R01은 01~05/08/30/35/36, R02는 01/06~20/26/31/32/34~36, R03은 02/07/13~21/25/28~33, R04는 21~24/34, R05는 01/06~20/22~27/29/31/34/35, R06은 역할별 화면과 각 조작 사례, R07은 전체 판정 기록과 32/33/35/36으로 추적합니다.

- 전역 최적성이나 모든 입력의 가능/불가능을 수학적으로 증명하지 않습니다. 최단 도보 배정 후 탐색하므로 다른 도보 후보로 바꾸면 가능한 해를 놓칠 수 있습니다. 오류/INFEASIBLE 원인과 관련 제약을 숨기지 않습니다.
- 작은 집합을 넘으면 삽입 휴리스틱을 쓰고 개선 탐색 평가는 제한됩니다. 제공 데이터에서는 실행 가능 케이스를 모두 풀었으나 임의 대형 데이터의 성공률과 응답시간은 보장하지 않습니다.
- 단일 서버 프로세스 전제의 버전 검사와 SQLite 저장입니다. 다중 서버/프로세스, 대규모 동시 접속, 장시간 부하, 디스크 장애 복구를 검증하지 않았습니다. 상태/이력을 통째 JSON으로 저장하고 화면이 주기 조회하므로 큰 데이터의 비용이 늘어납니다.
- HTTP에 Secure 쿠키를 사용할 수 없어 전송 도청 위험이 있습니다. 데모 암호, 계정 관리 부재, 무제한 장기 이력 저장은 실제 운영 전 개선 대상입니다. 로그인 제한은 프로세스 메모리 기반입니다.
- CSV 내보내기는 CSV 인용을 적용하지만 임의 등록 ID가 스프레드시트 수식으로 해석될 가능성에 대한 별도 중화는 아직 없습니다. 제공 합성 데이터에는 수식 ID가 없습니다.
- 모든 UI 요소와 반응형/접근성/다양한 브라우저를 수동 검사한 것은 아닙니다. 사용자 UAT 범위 밖은 NOT_RUN입니다.

8. 예상 서술형 질문과 답변
Q1. 프론트엔드부터 저장과 계산까지 어떻게 연결됩니까?
- 답변: HTML/JS 화면이 같은 로컬 서버의 API를 호출하고, 서버가 역할과 입력 버전을 확인한 뒤 검증한 데이터를 SQLite 트랜잭션으로 저장합니다. worker가 전체 기간을 계산하고 verify.cjs를 통과한 최신 버전 결과만 API와 화면에 제공합니다.
- 근거: public/app.js의 api/refresh, server.cjs의 begin/calculate, store.cjs의 save, planner.cjs의 solve, verify.cjs의 inspect.
- 한계: 단일 서버 프로세스 구조이며 다중 서버 조정은 구현하지 않았습니다.
Q2. 어떤 정책을 누가 선택했고 결과에 어떻게 반영됐습니까?
- 답변: 참가자가 D01에서 B를 명시적으로 선택했습니다. 최대와 평균 승차시간을 먼저 줄이도록 후보를 비교해 초기 후보의 최대 91분을 55분으로 낮췄으며 차량 5→6대, 편수 120→174 증가도 함께 표시합니다.
- 근거: decision.json, planner.cjs의 compare와 optimization, artifacts/route_plan.json.
- 한계: A는 미선택이며 거절한 것으로 기록하지 않습니다. 사용자의 추가 선택 이유는 확인되지 않았고 전역 최적성 증명도 없습니다.
Q3. 왜 이 알고리즘을 사용했고 대안은 무엇입니까?
- 답변: 작은 정류장 묶음에서 분할과 순열을 직접 비교하면 설명과 검산이 쉽고 외부 최적화 패키지 없이 실제 데이터에 대응할 수 있습니다. 여러 후보와 승차시간 경계를 탐색한 뒤 전체 지표로 개선합니다. 통합 수리 최적화는 더 큰 탐색을 할 수 있으나 이번 구현에는 사용하지 않았습니다.
- 근거: planner.cjs의 bestPath, partition, evaluate, ride-bound search, coordinate descent와 BASE/S1~S5 테스트.
- 한계: 도보 후보 배정과 차량 배차까지 통합 최적화하지 않아 해를 놓칠 수 있습니다.
Q4. 데이터 변경이 단순 버전 변경에 그치지 않았다는 증거는 무엇입니까?
- 답변: S1의 실제 직원 출퇴근 수요가 빠지고 추가되며 S2의 새 방향 이동시간으로 순서/시각/지표를 재계산합니다. 테이블 편집과 정책 저장도 수동 계산 버튼 없이 worker를 실행합니다.
- 근거: tests/service.test.cjs의 실제 시나리오 및 HTTP 자동 재계산 테스트, UAT01 사용자 PASS, history와 input_evidence.
- 한계: 변경된 간선을 사용하지 않는 일부 운행은 수치가 같을 수 있습니다. 노선 변경 자체를 성공 기준으로 삼지 않습니다.
Q5. 인증·인가와 HTTPS는 어떻게 처리했습니까?
- 답변: 초기 암호는 scrypt 해시로 저장하고 난수 세션과 HttpOnly/SameSite 쿠키를 사용합니다. 서버에서 ADMIN 역할과 직원 소유권을 검사하고 CSRF/Origin 검사와 출력 이스케이프를 적용했습니다. HTTPS는 요구되지 않은 로컬 HTTP 과제 범위라 구현하지 않았습니다.
- 근거: store.cjs의 passwordHash/login/session, server.cjs의 admin/employee API, 로그인/IDOR/CSRF 자동 테스트.
- 한계: 전송 암호화가 없으므로 실제 공개 운영에 적합하지 않습니다. TLS와 운영 계정 체계가 추가로 필요합니다.
Q6. 동시에 변경하거나 서버가 재시작되면 어떻게 됩니까?
- 답변: 요청 본문을 읽은 뒤 현재 데이터/정책 버전을 다시 확인하고 오래된 수정은 409로 거부합니다. 새 확정 버전이 들어오면 이전 worker를 취소하고 작업 번호/버전 검사로 구결과 게시도 막습니다. 완료한 상태는 DB에 보존하고 계산 중 재시작이면 현재 입력으로 복구 계산합니다.
- 근거: server.cjs의 expected/begin/calculate와 HTTP 동시 변경/READY 재시작 테스트, store.cjs의 openStore.
- 한계: 여러 서버 인스턴스가 같은 DB에 접근하는 운영은 검증하거나 설계하지 않았습니다.
Q7. 불가능한 데이터와 경계 조건을 어떻게 확인했습니까?
- 답변: S3의 접근 불가능자를 누락하지 않고 날짜/직원/방향별 64건 미배정 사유로 보고했습니다. 45/46명, 도보 18분, 승차 95분, 야간 익일과 휴무 제외를 검사하고 잘못된 결과를 주입해 독립 검산기가 적발하는지도 확인했습니다.
- 근거: verify.cjs의 inspect, tests/service.test.cjs, artifacts/test-results.txt.
- 한계: 알고리즘이 보고한 INFEASIBLE이 언제나 수학적 불가능 증명은 아닙니다. 임의 대규모 입력은 미검증입니다.
Q8. AI와 사람이 각각 무엇을 했고 무엇이 아직 미검증입니까?
- 답변: Codex는 전체 입력 감사, 코드, 로컬 자동 검사와 제출 전 문서를 작성했고 참가자는 정책 B를 선택하고 Browser UAT01과 UAT02를 직접 수행했습니다. 외부 AI/API/데이터 전송/Computer Use는 사용하지 않았습니다. 자동 테스트 12건과 사용자 두 역할 UAT가 모두 PASS입니다.
- 근거: 실제 대화 D01/UAT01 응답, decision.json, 테스트 결과 파일, 이 파일의 UAT 기록.
- 한계: 사용자 응답 없는 테스트를 사용자 PASS로 취급하지 않습니다. 제출 확정 후 후속 서술형에는 AI가 관여하지 않습니다.
