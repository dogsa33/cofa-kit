# 모의 2차 예선 과제 | 구성원 통근버스 노선 자동 생성 웹서비스

> **비공식 재현·연습 문제**입니다. 실제 Cofa Probe 시험의 원문/정답/채점표가 아닙니다. 모든 구성원/좌표/계정은 합성 데이터입니다. 이 저장소 자체는 **문제지**이며 **완성된 웹앱이나 노선 생성 정답이 들어 있지 않습니다.**

## 배경

2개 사업장과 여러 근무조를 운영하는 조직에서 통근버스 배차를 수작업으로 수행하고 있습니다. 근무자·휴무자 변경, 정류장 폐쇄, 도로별 이동시간 변동이 발생할 때도 예전 노선이 그대로 유지되는 문제가 있습니다. **운영자가 데이터와 운행 조건을 관리하고, 구성원은 자신에게 배정된 출퇴근 노선만 조회하는 웹서비스**를 구현하세요.

**핵심 평가 대상은 UI 이미지가 아니라 실제 데이터 기반 계산과 변경 전파입니다.** 데이터가 수정되면 서버가 새 데이터를 받아 **정류장 배정 → 노선 방문 순서 → 정류장 시각 → 차량 배차 → 구성원 탑승시간**을 다시 산출해야 합니다. 단순히 최신 날짜나 버전만 바꾸거나 캐시된 노선을 다시 그리는 것은 불합격입니다.

## 제공 자료

- `datasets/base/`: 정상 기준 데이터셋 10개 CSV 및 `constraints.json`
- `datasets/S1_*` ~ `S5_*`: **전체 스냅샷** 형태의 정상 구조 데이터 변경 케이스
- `datasets/E1_*` ~ `E4_*`: 오류가 포함된 데이터셋. 기존 정상 적용 버전을 훼손하면 안 됨
- `DATA_DICTIONARY.md`: 열·키·시간 규칙
- `OUTPUT_CONTRACT.md`: 결과 `route_plan.json` 형식
- `SCENARIOS.md`: 변경 재계산 시나리오
- `tools/check_datasets.py`: **입력 형식 검사기만** 제공. 노선 생성/인증/프론트/DB/백엔드 코드 없음
- `tests/test_fixtures.py`: 제공 데이터셋 자체의 정합성만 검사

과제 작업 중 공개 키트를 별도로 사용하려면 실제 과제 폴더에 `.cofa-kit`으로 복제하세요. 문제의 `README.md`, 원본 CSV 및 기타 파일을 덮어쓰지 마세요.

## R01. 로그인과 권한

- 운영자(ADMIN)와 구성원(EMPLOYEE) 로그인/로그아웃, 로그인 세션 유지, 잘못된 로그인 거부.
- `demo_accounts.csv`는 **초기화 시에만 사용하는 합성 임시 암호**입니다. DB에는 암호 원문 저장 금지, 암호 해시 저장. 세션 비밀키를 소스에 고정하지 말 것.
- 운영자만 CSV 선택·적용, 데이터 수정, 운행 조건 변경, 노선 재계산, 전체 운행 결과 열람, 변경 이력 열람 가능.
- 구성원은 날짜별 본인 출근·퇴근 탑승 정류장/시간, 노선 방문 순서 및 본인 사업장만 조회 가능. 프론트에서 메뉴를 숨기는 것만으로는 불충분하며 **서버 API의 역할 및 소유권 검사를 필수 구현**.

## R02. 데이터 관리와 검증

- 운영자는 전체 스냅샷(기준/시나리오)을 목록에서 선택하거나 CSV 묶음을 등록할 수 있고, 현재 적용 버전과 마지막 검증 결과를 확인합니다.
- 데이터의 필수 열·자료형·날짜 형식·ID 존재·중복키·참조 무결성·방향별 이동시간 완전성·음수/0값·정원·근무상태를 검증합니다. 오류는 **파일명/행/컬럼/이유**를 표시합니다.
- 실패 스냅샷은 **원자적으로 적용 거부**하며 이전 유효한 데이터/노선/버전을 유지합니다.
- 운영자 UI에서 **최소한 `shifts`의 근무상태, `stops`의 활성 상태, `travel_times`의 이동시간 값**을 직접 수정하고 저장할 수 있어야 합니다. 유효성 검사에 성공하면 변경이 적용됩니다.
- DB 또는 파일 기반 영속 저장을 사용합니다. 서버 재시작 후 적용 데이터, 정책, 마지막 결과, 변경 이력이 보존되어야 합니다.

## R03. 배정 및 노선 계산

노선은 사전 고정된 정류장 배열이나 예제 결과를 반환하지 않고 실제 입력에 의해 생성해야 합니다.

1. 지정 기간 내 **근무일**이며 `shifts.status=WORK`인 활성 구성원만 배정합니다. `OFF/LEAVE/TRAINING`은 제외. 야간조 종료가 익일이면 정확한 날짜로 처리합니다.
2. 활성 정류장 중 `access_times.csv`의 **도보시간이 제약 이내**인 후보에 구성원을 배정합니다. 최단 접근시간을 우선할 수 있지만, 최종 정책은 전체 노선·시간 제약과 함께 설명해야 합니다.
3. 직원은 자신의 사업장에 해당하는 출근/퇴근 노선을 **각각 정확히 1회** 받아야 합니다. 한 운행에 다른 사업장 탑승자를 혼합하지 않습니다.
4. 방향이 있는 `travel_times.csv` 간선을 사용하여 정류장 방문 순서와 정류장 도착/출발 시각을 계산합니다. **A→B와 B→A를 같은 값으로 간주하면 안 됩니다.** 미존재 간선이나 직선거리 대체는 금지.
5. 출근은 해당 구성원의 근무 시작 **20~40분 전** 사업장 도착, 퇴근은 근무 종료 **10~30분 후** 사업장 출발. 지나치게 이른 출근 도착 또는 과도한 퇴근 대기 역시 위반으로 처리합니다. 다중 근무조가 혼재할 때 구성원별로 검사합니다.
6. 차량 좌석 수(기본 45석) 이내, 모든 운행 연결 경로/정류장 시각/최대 탑승시간/도보시간/활성 정류장 제약을 준수합니다. 정류장 정차시 최소 2분 확보. 차량 중복 배차 금지; 차량 재사용 시 선행 운행 종료점에서 후속 운행 시작점까지의 **공차 이동시간 + 회차 여유시간 10분** 확보. 미사용/비활성 차량 배정 금지.
7. 충족 가능한 노선을 계산하지 못했을 때 **조용히 인원을 누락하거나 제약을 무시하지 말고** `INFEASIBLE` 및 미배정 직원/사유/관련 제약을 출력합니다.
8. 차량 수, 전체 운행 횟수, 총 운행시간, 평균/최대 승차시간, 평균/최대 도보시간, 제약 위반 수치를 함께 산출합니다. 운행 횟수와 실제 차량 대수는 별개 지표입니다.

고정 안전 제약은 `datasets/base/constraints.json` 및 `DATA_DICTIONARY.md`를 따릅니다.

## R04. 최적화 선택 — 참가자 Human-in-the-loop

**다음 조건은 과제에서 일부러 미확정했습니다.** 프로그램이 임의로 정답을 확정하지 않고 실제 사용자에게 A/B(/C) 대안, 추천, 예상 장단점을 설명해 **한 가지 중요한 결정을 묻고**, 사용자 응답을 받은 뒤 해당 정책으로 구현하세요.

- **무엇을 우선 최적화할 것인가?** (예: 필요한 차량 대수, 전체 운행 횟수, 총 운행시간, 직원 평균/최대 승차시간)
- 선택한 **우선순위 순서 또는 가중치**를 운영자 화면에서 보고 수정 가능하게 합니다.
- 사용자 응답 없이 AI 추천을 승인한 것으로 기록하지 않습니다. 선택/명시적 거절/미선택 및 채택 근거를 기록합니다.
- 최적화 해법의 전역 최적성을 증명할 필요는 없지만 **설명 가능한 휴리스틱 + 제약 검사 + 개선 전/후 목적 지표**를 제시해야 합니다. 무작정 랜덤 결과를 내거나 정적 노선을 복사하면 안 됩니다.

## R05. 데이터 변경 → 자동 재계산 (최중요)

- 정상 스냅샷 적용 또는 UI를 통한 근무표·정류장·이동시간 변경이 **실제 확정 저장**되면 `dataset_version`을 증가시켜 관련 전체 기간 노선을 자동 재계산합니다. 수동 `재계산` 버튼을 누르지 않아도 됩니다.
- 운행 최적화 정책 변경 시 `policy_version`이 증가하고 자동 재계산합니다.
- 상태: `UPDATING → CALCULATING → READY` 또는 `ERROR/INFEASIBLE`. 재계산 전 옛 결과는 `STALE`로 표시하고 최신 성공 결과로 위장하지 않습니다.
- 예컨대 `ST03→ST04`가 10분에서 18분으로 바뀌면, 새로운 이동시간을 사용해 노선 순서·정차시각·전체 운행시간을 **다시 계산**해야 합니다. 단, 새 계산에서 최선의 노선 순서가 우연히 이전과 같을 수 있으므로 **무조건 노선이 달라야 한다는 뜻은 아닙니다.** 재계산 시각, 입력 버전, 변경 내역과 해당 방향의 새 이동시간 반영 근거를 확인할 수 있어야 합니다.
- 재계산 중 여러 번 변경되면 **마지막 확정 데이터/정책 버전의 결과만 현재 결과로 게시**합니다. 실패 시에는 원인과 영향을 표시하고 이전 결과는 최신이라고 표시하지 않습니다.
- 변경 전후 비교 화면(차량 수·운행 횟수·총 운행시간·평균 및 최대 탑승시간·미배정 건수)을 제공합니다.

## R06. 웹 화면

- **공통**: 로그인/로그아웃, 사용자·역할 표시, 현재 데이터 버전·계산 상태.
- **운영자**: 데이터셋 선택→검증→적용, CSV/테이블 편집, 운행 조건 변경, 노선 재계산 상태, 기간/사업장/근무조별 전체 노선 표, 노선도 및 통계, 변경 이력, 결과 JSON/CSV 내보내기.
- **구성원**: 본인 날짜 선택→출근·퇴근 운행 ID, 정류장, 탑승/하차 시각, 노선 순서, 도보 접근시간. 권한 밖 직원·운영자 메뉴/API 접근 불가.
- **노선 시각화**: 제공한 `nodes.csv`의 합성 2D 좌표로 SVG/Canvas 등을 사용하여 정류장·사업장·방향을 표현합니다. 실제 지도 SDK나 GPS 서버는 필요 없습니다. 시각화는 **현재 계산 결과**를 사용해야 합니다.
- 서버는 제공 Browser에서 연결 가능한 실제 포트/바인딩(예: `0.0.0.0`)으로 실행하고 접속 URL을 명확하게 안내합니다. HTTPS/외부 배포를 요구하지 않습니다.

## R07. 검증과 설명

- 정상/경계/오류 케이스 자동 테스트: 역할·IDOR, 45명 초과, 근무·휴무 배정, 시간 제약, 야간조, 방향 이동시간, 원본 불변성, 차량 겹침, 데이터 변경 후 자동 재계산, 잘못된 데이터 적용 원자성, DB 재시작 지속성.
- 운영자와 구성원 역할 각각 **사람이 직접 브라우저에서 검증**할 수 있도록 1건씩 단계/입력/예상결과를 안내하고 실제 PASS/FAIL/NOT_RUN/BLOCKED를 기록합니다.
- 코드/변경/사용자 결정·거절/검증 근거/미구현·한계를 담은 `IMPLEMENTATION_REPORT.md`를 제출합니다. 유효성 확인 없이 PASS라고 쓰지 마세요.

## 결과물

1. 실행 가능한 **프론트엔드 + 백엔드 + 데이터 저장소** 전체 코드. 기술 스택 선택은 자유이나 실제 제공 환경에서 실행해야 합니다.
2. `README_RUN.md`: 최초 설치·실행·테스트 명령, 테스트 계정, 서버 포트, 데이터 버전 반영 방식. 비밀정보 또는 실제 사용자 데이터 포함 금지.
3. `artifacts/route_plan.json`: `OUTPUT_CONTRACT.md`에 맞는 **실제로 계산한 기준 데이터셋 운행 계획**. 불가능 시 기계적으로 검토 가능한 실패 내용 및 사유.
4. `IMPLEMENTATION_REPORT.md`: 요구사항별 구현/검증 상태, 인간 의사결정 기록, 알고리즘·제약·자료변경·잔여 위험 설명.
5. **테스트 실행 결과**: 명령 및 실제 출력 또는 보고서 경로. 시험의 실제 제출 위치/형식이 별도로 주어지면 그것이 우선입니다.

## 구현 순서 권장 (제한시간 4시간 가정)

이 문제는 **입력 자체가 불가능한 데이터는 아니지만**, 모든 운영 기능을 완성하는 것은 고난도입니다. 우선 최소 동작 흐름을 완료하고 이후 범위를 확장하세요.

1. **핵심 흐름**: 실제 데이터 로드/검증 → 사용자 정책 선택 → 최소 설명 가능한 휴리스틱 → 정원/시간 검사 → JSON 생성.
2. **서비스 연동**: 로그인/서버측 권한 → 운영자 데이터 수정·적용 → 자동 재계산/버전·상태 → 구성원 조회.
3. **실제 검증**: S1/S2 재계산 → S3 의도된 INFEASIBLE → E1~E4 원자적 거부 → 수동 UAT.
4. **시간이 남으면**: 지도/SVG 개선, 차량/회차 최적화, 변경 전후 비교, 추가 보안·성능 검사.

실제 구현 범위가 제한시간 안에 끝나지 않으면 미구현·미검증 상태를 정확히 표시합니다. 단순화된 휴리스틱이어도 **고정 노선 반환이나 재계산 생략은 허용하지 않습니다.**
