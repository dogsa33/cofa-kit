# 통근버스 노선 과제 — 공개 자료 기반 합성 연습

**이 폴더의 CSV·JSON은 모두 이번 연습을 위해 새로 만든 합성 데이터입니다. 실제 Cofa 시험 제공 파일·정답·공식 요구사항이 아닙니다.** 실전에서는 과제 README와 담당자 답변을 우선합니다.

## 참고한 공개 자료와 출처 구분

- 공개 사전설계 문서: https://github.com/Hantastic-02/h-kit/blob/main/study/04_%ED%86%B5%EA%B7%BC%EB%B2%84%EC%8A%A4_%EC%82%AC%EC%A0%84%EC%84%A4%EA%B3%84.md
- 원문은 **정류장 선정 → 구성원 배정 → 노선·시간표**, 관리자/구성원 웹 화면, 작업용 데이터셋 변경 시 재계산을 다룹니다.
- **원문이 README 요구사항이라고 서술한 조건(공개 문서의 주장):** 차량 45석/입석 없음, 출근 시작 20분 전까지 도착, 퇴근 종료 10분 이후 출발, 근무자는 출근·퇴근 각각 1회 배정·휴무자는 제외, `travel_times.csv` 방향별 이동시간 사용, 야간조 날짜 경계 고려.
- 문서의 예시 가정(예: 정류장 1.5 km, 최대 탑승 70분)은 **공식 필수조건으로 취급하지 않습니다.** 원문은 실제 시험 원본 자체가 아니므로 이 폴더는 모의 연습에만 사용합니다.
- 앱 구현 방식 참고용(별도): https://github.com/Yohannes33/route-optimization-api (FastAPI·OR-Tools 기반 직원 셔틀 배정 사례). **그 저장소의 알고리즘/코드를 이 연습 검증기에 복사하지 않았습니다.**

## 연습 데이터

| 파일 | 목적 |
| --- | --- |
| `employees.csv` | 가상 직원·정류장·사업장 관계. 개인 신상정보 없음 |
| `shifts.csv` | 각 직원의 근무/휴무, ISO 시각. 야간조는 퇴근이 다음 날짜 |
| `travel_times.csv` | **방향별** 이동 분수. 왕복 동일하다고 가정하지 않음 |
| `routes_valid.json` | 위 입력으로 작성한 **검증용 가상 노선 결과** |
| `verify_routes.py` | 앱이 생성한 JSON과 **분리하여** 제약을 확인하는 순수 Python 검증기 |

가상 JSON에서 각 `trip`은 한 차량의 한 번 운행이고, `direction`은 `inbound`/`outbound`입니다. `employee_ids`는 해당 운행을 이용하는 직원 ID 배열, `legs`는 차례대로 연결되는 구간(`from`, `to`, `depart_at`, `arrive_at`)입니다. 동일 직원이 각 근무일 **출근 1회, 퇴근 1회**인지 확인합니다. 이동시간은 CSV와 정확히 같도록 구성했고, 정차 대기는 구간 간의 시각 차이로만 표현했습니다.

```bash
# 저장소 루트에서 실행. 외부 패키지 설치 필요 없음
python examples/shuttle/verify_routes.py --data-dir examples/shuttle --routes examples/shuttle/routes_valid.json
python -m unittest discover -s tests -p 'test_shuttle_routes.py' -v
```

## 모의 개발·검증 시나리오

1. 실제 과제가 주어졌다고 가정하고 해당 README를 먼저 읽어 `R-ID`를 만들되, **여기 적힌 합성 조건을 실제 시험 요구로 오인하지 않습니다.**
2. 관리자가 `shifts.csv` 등 데이터를 변경하면 파싱·검증 → 적용 → 재계산 → 화면/내보내기 결과가 변하는지를 테스트합니다.
3. **HITL:** 차량 수 우선 vs 탑승 시간 우선은 과제에 이미 명시돼 있지 않을 때 사용자에게 비교·추천 후 **답을 받아 결정**합니다. 정원·도착 시각 같은 명시된 필수조건은 임의로 완화하는 선택지가 아닙니다.
4. **자동 검사:** `verify_routes.py`로 배정 누락·중복·휴무자 배정·용량·시각·이동시간·야간조 경계를 독립 확인합니다. 앱이 내보내는 JSON이 이 연습 JSON 형식과 다르면 작은 변환기를 작성하거나 검증기를 실제 스키마에 맞게 조정하되, 기대 조건을 실제 잘못된 출력에 맞춰 완화하지 않습니다.
5. **수동 UAT:** Codex가 한 번에 하나의 실제 화면 테스트, 실행 포트/행동/기대 결과를 안내 → 사람이 Browser에서 실행 → 관찰과 PASS/FAIL/NOT_RUN/BLOCKED 보고 → 동일 시나리오 재검증.
6. **위험 검증:** 누락된 열, 근무/휴무 전환, 정원 45→46명, 관리자 API 접근 제한, 동시 편집 2개, 데이터 재시작·저장 상태 등 **과제에 존재하는 위험에 한해** 테스트합니다. 외부 공격·고부하 테스트는 하지 않습니다.

## 이 검증기의 의도적 범위와 한계

- **검증기 ≠ 최적화기·웹앱.** 해를 생성하거나 최소 차량 수·최소 운행시간의 최적성을 증명하지 않습니다.
- 합성 JSON의 명시된 경로에 대해 제약을 확인합니다. 실제 도로 교통·정류장 좌표·중간 승하차 시각·운전자 근무시간은 모델링하지 않습니다.
- 관리자 인증·API, 실시간 지도·동시접속·DB 저장은 이 예제에 없습니다. 이런 것은 **실제 웹앱을 만든 연습**에서 별도로 테스트해야 합니다.
- 한 테스트가 통과해도 큰 입력 규모·모든 동시성 상황의 안전을 보장하지 않습니다.

기존의 `examples/defects.csv`, `examples/joins/`, `examples/semiconductor/` 및 이 키트의 `tests/test_data_tools.py`는 별도 예제로 유지합니다. 과제별 입력과 합성 예제는 서로 구분합니다.
