# 단일 Codex 진행 시나리오 — 제출 확정 전 단계 전용

다음 작업을 **하나의 Codex가** 진행한다. 별도 서브에이전트나 병렬 위임 없음. 실제 과제 README 및 운영 안내가 이 지침보다 우선한다.

## 사용자에게 보이는 모든 보고는 평문

- Cofa 에디터는 Markdown 원문이 보일 수 있으므로 일반 보고(초기 분석, 현업 질문, 계획, HITL, 검증, 최종 Q&A)는 1. 제목 같은 평문 제목과 - 하이픈 목록만 사용한다.
- 꾸밈 기호 **, # 제목, | Markdown 표, 코드 펜스, > 인용, Markdown 링크를 사용하지 않는다. 질문·데이터 검사는 표 대신 항목별 - 목록으로 출력한다. 실제 과제의 코드와 필수 제출 데이터 형식은 임의로 바꾸지 않는다.
- 제출 확정 전에는 실제 과제 폴더의 FINAL_REVIEW.md 한 파일에 최종 요약과 예상 질문 답변을 평문으로 저장·갱신한다. 추가 파일이 금지된 과제에서는 Codex 대화에만 출력한다. ../skills/cofa-explain/SKILL.md 적용.

## 시간 관리 — 공식 타이머 기준, 180분 목표 예산

- 실제 과제 시작 직후 참가자에게 **Cofa 화면의 공식 남은 시간**을 한 번 확인받고, 허용된 터미널에서 시스템 시각(`date '+%Y-%m-%d %H:%M:%S %Z'`, PowerShell이면 `Get-Date`)을 기록한다. **Codex가 공식 타이머를 자동으로 읽는다고 가정하지 않는다.** 서버 시계와 공식 타이머가 다르거나 타이머를 볼 수 없으면 공식 화면을 우선하고 참가자에게 확인을 요청한다. 현재 시각이나 남은 시간을 추측하지 않는다.
- 다음 시간은 **180분 과제 시작 후 누적 목표(가이드라인, 하드 타임아웃 아님)**이며, 과제 난이도와 **공식 남은 시간**에 따라 조정한다.

| 경과시간 | 시간 예산 | 단계 목표 |
| --- | ---: | --- |
| 0~15분 | 15분 | README/AGENTS·제출 조건 확인, 데이터셋 감사(확인한 범위 명시) |
| 15~25분 | 10분 | 현업 확인 질문 목록, 구현 계획·전략, 긴급 핵심 HITL |
| 25~100분 | 75분 | 필수 R-ID 기능 중심 구현. 선택 기능·장식 후순위 |
| 100~120분 | 20분 | 기능 연결, 실행 확인, 1차 자동·경계 테스트 |
| 120~150분 | 30분 | 독립 검산, 변경 후 재계산, 사용자 Browser UAT |
| 150~165분 | 15분 | 중요한 FAIL 수정·관련 회귀 테스트 |
| 165~170분 | 5분 | FINAL_REVIEW.md 최종 갱신·예상 Q&A, 저장/제출 체크 |
| 170~180분 | 10분 | 참가자 제출 확인 및 오류 대비 예비 시간 (공식 종료시각 전) |

- **시점별 전환 확인:** 시작, 25·100·120·150·165·170분 부근의 **실제 작업 전환 때만** 현지 시스템 시각·경과시간을 확인한다. 정기 자동 알림이나 시간 측정 백그라운드 작업을 약속하지 않는다. 공식 남은 시간을 모르면 참가자가 알려준 마지막 값의 기준시각을 표시하고, 중요 전환 또는 제출 직전에 재확인한다.
- **120분 시점은 1차 완성 목표:** 구현이 부족해도 검증을 무조건 생략하지 말고 현재 R-ID별 PASS/FAIL/NOT_RUN과 가장 큰 제출 위험을 제시한다. 제한시간이 부족하면 필수 기능·기본 검증·결과 저장을 우선하고 선택적 UI 장식·중복 보고서·과도한 재설계를 중단한다. **필수 요구를 조용히 빼거나 검증하지 않고 PASS 처리하지 않는다.** 범위 변경이 중요하면 한 건의 HITL로 근거와 손실을 설명한다.
- **170분 전 제출 우선:** 공식 마감 **최소 10분 전부터 제출 절차**에 집중하고, 저장 상태·필수 파일 경로·실제 검증·미완료 사항을 확인한다. 이미 제출했다면 다시 시간을 채우지 않는다. 시스템 시각이 170분 경과를 가리켜도 **실제 남은 시간과 공식 종료시각 중 더 이른 제약**을 따른다. 제출 확정은 반드시 참가자가 수행하며 Codex가 제출을 확정했다고 가정하지 않는다.
- **서술형 대비:** 작업 중 D-ID 선택/거절, AI에게 맡긴 작업, 알고리즘 이유, 극단적 사례·다중 접속 한계, 테스트 증거를 누적 기록한다. 개발 과정에서 쌓은 근거를 바탕으로 제출 전 FINAL_REVIEW.md 한 파일에 평문 예상 Q&A로 요약한다. **제출 확정 및 후속 서술형 단계에서는 AI가 관여하지 않는다.**

## 신규 과제의 고정 순서 — 사전 분석 보고 전 기능 개발 금지

다음 1~4단계는 **순서대로 실제 조사·보고하는 필수 게이트**다. README를 읽거나 질문 목록만 출력했다는 이유로 데이터 감사가 완료됐다고 주장하지 않는다. 기존 과제를 이어서 수정할 때는 이미 검증된 결과를 재사용하되 영향받는 요구·데이터는 재확인한다.

1. **과제 및 요구사항 분석** — 실제 과제 작업 위치, README·AGENTS.md·기존 코드, 입출력, 제출 조건·금지사항을 확인하고 R-ID별 필수 요구를 정리한다. `.cofa-kit/examples/`은 실제 과제 데이터가 아니다. `../skills/cofa-triage/SKILL.md` 적용.
2. **전체 데이터셋 목록화·실제 데이터 감사** — 발견한 모든 입력 데이터셋과 변경 시나리오를 목록화해 용도, 파일별 행·열 수, 컬럼·형식·키, 관계를 설명한다. **실제 파일을 조사해** 결측·중복 키·참조 무결성·값 범위·날짜·시간대·논리 오류를 확인한다. 기준 데이터와 변경 데이터는 차이·영향을 구분한다. 명령/검사 범위(전체/표본/NOT_RUN)와 데이터 품질 문제·예상 영향·원본 보존 여부를 보고한다. 큰 데이터는 검사를 효율화하되 확인하지 않은 부분은 검증한 것처럼 쓰지 않는다.
3. **현업 확인 질문 목록 산출** — **첫 분석 결과에 반드시 포함한다.** 위 감사와 과제 근거에서 **정말 미확정인 업무 사실**만 Q-ID·P0/P1/P2·대상·근거(README·파일·컬럼)·답변 영향·상태와 함께 한 번에 보고한다. README에 답이 있는 질문이나 사용자가 선택할 설계 판단은 현업 질문에서 제외한다. 없으면 `현업 확인 질문 없음` 및 **확인한 근거·감사 범위**를 제시한다. 질문 전달은 참가자가 현업 담당자에게 직접 한 건씩 수행한다.
4. **개발 계획·전략 보고** — 필수 요구의 `dropped`·`skip`·`NOT_RUN`은 성공이 아니며 미완료로 추적한다. R-ID 우선순위, 입출력·데이터 흐름, 구조·기술 스택, 계산/알고리즘 후보, 데이터 변경에 따른 재계산·오류 복구, 자동 검증·사용자 UAT, 제약·리스크·미확정 사항을 짧고 구체적으로 제시한다. **1~4단계의 실제 결과를 사용자에게 보고하기 전에는 본격적인 웹앱/알고리즘 구현을 시작하지 않는다.** 다만 읽기 전용 조사·임시 데이터 점검 스크립트는 허용한다. 기존 과제의 기록을 재사용하며 문서·폴더를 과도하게 늘리지 않는다.
5. **핵심 설계 HITL** — 현업 문의(업무 사실)와 참가자 결정(최적화 우선순위·정책 등)을 구분하고, 중요 결정은 `../skills/cofa-decide/SKILL.md`에 따라 **한 번에 한 결정**: 대안·근거·추천·위험 → 실제 답변 대기 → 선택·명시적 거절·미선택 기록. AI 추천·"알아서"·UAT PASS는 승인 아님. 미해결 P0 때문에 확정할 수 없는 부분은 보류하되 독립적인 승인 범위의 작업은 진행할 수 있다.
6. **최소 구현·반복 검증** — `../skills/cofa-build/SKILL.md`로 기존 코드·스택 우선 구현. `../skills/cofa-verify/SKILL.md`로 정상·경계·오류, 데이터 변경에 따른 실제 재계산, 보안·중복·동시성 등 과제 관련 위험을 실제 실행해 확인한다. 변경 전 PASS를 그대로 재사용하지 않는다. 개발 도중 새 중요 판단이 나오면 5단계 HITL을 다시 적용한다.
7. **사용자 수동 UAT** — UI 과제에서만 `../prompts/UAT.md` 지침으로 실제 포트/입력/조작/사전 기대결과를 한 건씩 안내 → 사용자 PASS/FAIL/NOT_RUN/BLOCKED와 관찰 기록 → 필요시 수정·재검증. UAT PASS는 업무 정책 승인과 별개.
8. **최종 설명·예상 질문 대비 (제출 확정 전)** — `../skills/cofa-explain/SKILL.md`로 현재 코드·데이터 흐름, 사용자 결정·거절, 실제 검증·미검증, 취약점·한계를 정리한다. **실제 작업 증거에 기반한 예상 질문·핵심 답변 목록(6~10개)을 필수로 출력**하여 참가자가 구현을 직접 설명할 수 있는지 확인한다. 질문 범위는 아키텍처·HTTPS/보안·알고리즘·AI 활용/비활용·HITL·극단적 케이스·동시 접속·검증·한계를 과제 적합성에 맞춰 선택한다. 실제 과제 폴더의 FINAL_REVIEW.md 한 파일에 평문 제목과 - 목록으로 저장하고 대화창에는 경로·핵심 사항을 보여준다. 추가 파일이 금지되면 대화 보고로 대체한다. 미구현·미검증을 완료로 꾸미지 않고, 남은 시간이 부족하면 중복 설명보다 필수 검증·제출을 우선한다. **제출 확정 후에는 AI가 실제 후속 서술형 예상/답변 생성도 포함해 모든 작업을 즉시 중단한다.**

추가 선택 지침:
- 반도체 계측·수율·조인/SPC 데이터가 실제 과제에 있으면 `../skills/cofa-semiconductor/SKILL.md`만 추가로 읽는다.
- 모델 학습·평가 과제라면 `../skills/cofa-model-eval/SKILL.md`만 추가로 읽는다.
- 통근버스 예제는 사전 연습 요청이 있을 때만 `../examples/shuttle/README.md`를 읽는다.
- **스킬 파일은 동작 규칙이지 독립 에이전트가 아니다.** 사용자가 매 단계 선택할 필요 없다.
- 외부 API, 개인 키, Git Push, 브라우저 자동화, 시험 내용 외부 전송은 하지 않는다. 후속 AI 사용 금지 단계에 들어가면 중단한다.

매 응답은 `실제로 한 일 / 확정된 기준과 결정 대기 / 검증됨·실패·미검증 / 다음 행동`을 짧게 제공한다. 모호한 기준만 사용자에게 묻고, 사소한 구현 질문을 늘리지 않는다.
